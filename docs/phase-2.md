Good. Now Phase 2 = Users. Since your goal is to learn rather than just copy code, we'll build it as a small vertical slice.

The goal is:

POST /users
GET  /users/{user_id}

We'll initially keep users in memory. Don't introduce PostgreSQL yet—that comes in Phase 3.

1. What we're building

Our API should eventually behave like this:

Create user
POST /users
Content-Type: application/json
{
  "name": "Santhosh",
  "email": "santhosh@example.com"
}

Response:

{
  "id": 1,
  "name": "Santhosh",
  "email": "santhosh@example.com"
}

Then:

GET /users/1

returns:

{
  "id": 1,
  "name": "Santhosh",
  "email": "santhosh@example.com"
}
Step 1 — Think about the data first

Before writing FastAPI code, let's design our user.

A user needs:

id
name
email

For now:

id       → integer
name     → string
email    → email

One important question:

Should id come from the client?

For example, should the client send:

{
  "id": 123,
  "name": "Santhosh",
  "email": "..."
}

No.

The server should generate the ID.

So we have two different concepts:

Data coming FROM client:

name
email

and:

Data generated BY server:

id

This leads us to our first important FastAPI/Pydantic concept.

Step 2 — Create a Pydantic model

You already encountered request bodies in Phase 1.

Create:

from pydantic import BaseModel, EmailStr


class UserCreate(BaseModel):
    name: str
    email: EmailStr

Now FastAPI understands what a valid user creation request looks like.

For example:

{
  "name": "Santhosh",
  "email": "santhosh@example.com"
}

is valid.

But:

{
  "name": "Santhosh",
  "email": "hello"
}

should fail because "hello" isn't a valid email.

That's the first major thing I want you to understand:

                    Request
                       │
                       ▼
              ┌─────────────────┐
              │    Pydantic     │
              │    Validation   │
              └────────┬────────┘
                       │
                  valid?
                 /       \
               yes        no
               │           │
               ▼           ▼
          Your code      422

FastAPI handles the validation for you.

Step 3 — Where do we store users?

We don't have PostgreSQL yet.

So let's deliberately use a Python dictionary:

users = {}

Imagine:

users = {
    1: {
        "id": 1,
        "name": "Santhosh",
        "email": "santhosh@example.com"
    },
    2: {
        "id": 2,
        "name": "Arun",
        "email": "arun@example.com"
    }
}

And we'll maintain:

next_user_id = 1

This is temporary storage.

Don't worry about persistence yet.

Step 4 — Create the POST endpoint

Your first implementation can be:

@app.post("/users")
def create_user(user: UserCreate):
    global next_user_id

    new_user = {
        "id": next_user_id,
        "name": user.name,
        "email": user.email
    }

    users[next_user_id] = new_user

    next_user_id += 1

    return new_user

Let's understand this instead of blindly copying it.

When this request comes:

POST /users

with:

{
  "name": "Santhosh",
  "email": "santhosh@example.com"
}

FastAPI creates:

user = UserCreate(
    name="Santhosh",
    email="santhosh@example.com"
)

Then:

user.name

gives:

Santhosh

and:

user.email

gives:

santhosh@example.com

We then generate:

id = 1

and save:

users[1] = {
    "id": 1,
    "name": "Santhosh",
    "email": "santhosh@example.com"
}
Step 5 — Create GET /users/{user_id}

Now implement:

@app.get("/users/{user_id}")
def get_user(user_id: int):
    if user_id not in users:
        return {"error": "User not found"}

    return users[user_id]

Now:

GET /users/1

FastAPI converts:

"1"

into:

1

because you specified:

user_id: int

This is another thing worth experimenting with.

Try:

GET /users/abc

FastAPI should reject it because:

abc ≠ integer
Step 6 — Your complete Phase 2 code

Your main.py might currently look something like:

from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()


class UserCreate(BaseModel):
    name: str
    email: EmailStr


users = {}

next_user_id = 1


@app.get("/health")
def health():
    return {"status": "ok"}


@app.post("/users")
def create_user(user: UserCreate):
    global next_user_id

    new_user = {
        "id": next_user_id,
        "name": user.name,
        "email": user.email
    }

    users[next_user_id] = new_user

    next_user_id += 1

    return new_user


@app.get("/users/{user_id}")
def get_user(user_id: int):
    if user_id not in users:
        return {"error": "User not found"}

    return users[user_id]

Don't worry if this looks simplistic.

It's supposed to be.

We're learning the mechanics before introducing architecture.

Don't just see that it fails. Look at the HTTP status code and response body.

One thing I want you to improve

Our current code has a problem:

if user_id not in users:
    return {"error": "User not found"}

That's actually not a good API design.

The server should return:

404 Not Found

rather than:

200 OK

with an error-looking JSON response.

We'll fix that using FastAPI's:

HTTPException

But I don't want you to blindly add it yet.

Before we move forward, understand this distinction:

HTTP 200
    ↓
Request succeeded

HTTP 404
    ↓
Resource doesn't exist

HTTP 422
    ↓
Request validation failed

HTTP 500
    ↓
Server-side failure
